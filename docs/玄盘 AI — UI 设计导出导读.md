**一句话概括这套 UI 的设计语言**：
以实物罗盘为视觉母题，用「暖米色纸感底 + 深蓝主色 + 朱红焦点」承载传统器具的质感；
而在真正"在测量"的那几页（拍摄、对盘、看传感器读数）整体转入深色仪器风，
让盘面刻度与磁针在暗底上像一台真正的测量仪表。
两套配色**共用同一套几何与角度换算** —— 几何是事实，配色是视角。

## 1. 先看懂这条约束链，它解释了大部分设计决定

这不是一个"按审美自由发挥"的界面。几乎每个看起来不寻常的设计决定，都是某条工程约束被翻译成视觉语言的结果。
按顺序读完下面六条，再去看页面源码，判断会准确得多。

### ① 计算层是唯一真源 → 界面零计算

术数计算全部由后端 Python 内核完成（RULE-001：**确定性计算必须由代码完成**）。
客户端因此**不含**任何五行、干支、纳音查表或公式 —— 否则就会出现两份口径，后端改了前端没跟，
用户看到的结论与算出来的不一致。

唯一的例外是 `src/lib/ring24.ts`：它内嵌了二十四山的**顺序与山心角**，因为环形选择器必须在**首帧**
就画出 24 个格子（等接口回来再渲染会先白屏再"啪"地出现格子）。属性（五行/卦/三元龙）仍走接口。
代价是顺序可能漂移，而漂移的后果是静默灾难 —— **用户点了「午」，算出「未」**。
所以设了两道防线，其中 `tests/mobile/test_ring24_parity.py` 会真正执行 `ring24.ts`、与 Python 内核逐位比对。

> 📌 分析这条 UI 时，请把「界面上的每个数字都来自 HTTP」当作前提；
> `08-api-contract.md` 里的 `types.ts` 就是这些数字的形状。

### ② 识别可能失败 → "未定"是一等状态，且不许画替代图形

识别置信度不足时，计算层返回 `null` 而不是猜（RULE-003）。界面必须如实呈现：

- `null` 一律渲染为 **「未定」**，绝不留空（留空会让人以为程序坏了）；
- **不许画会被误读的替代图形** —— 没有方位数据时如果画一个静止在 0° 的罗盘，
  用户会读成"方位就是 0°"。此时应显示虚线空盘 + 可操作提示。

`03-sensors.png` 与 `19-report.png` 是这条规则的两处实证。

### ③ 用户必须能修正 → 确认页是必经闸门，且修正不用角度输入

所有识别结果都要经用户确认才能进入计算（RULE-004）。
这条闸门同时是**产品最重要的安全机制**：识别可能给出"山名是错的"这种假阳性结果，
而用户看到的是一个**看似正常的错误坐向**，不会去重拍。唯一防线就是这道确认页。

界面上有两个刻意的"不方便"：

- **不给角度输入框。** 手动修正坐向的唯一入口是二十四山环形选择器。
  用户不知道 `177.03°` 是什么意思，但知道罗盘上「午」在哪；而 `17.7` 与 `177` 混淆会静默产生完全错误的结论。
- **向山不可独立选择。** 坐向是一条直线，向山必然是坐山的对宫。
  允许独立选会造出"坐午向巳"这种几何上不成立的状态 —— 在交互层就约束住，比让用户走到报错要好。

见 `17-confirm.png` / `02-adjust.png` 与 `CompassAdjuster.tsx`。

### ④ 规则不得散落 → 组件内禁写色值

对应 RULE-005。全 App 的色值/间距/字号只有一个真源：`src/theme/tokens.ts`。
组件里写死一个 `#013A6C`，就会出现"主色在这里是 `#013A6C`、在那里是 `#01366C`"的漂移，
而这种漂移肉眼几乎看不出来。

> 📌 如果你要评审"设计系统执行度"，**统计组件里的硬编码色值是有效的切入点** ——
> 按本项目的规则，正确值应当是 **0**。

### ⑤ AI 不得污染盘面事实 → 报告三标签物理分离

报告页固定三个标签：**盘面事实 ｜ 传统分析 ｜ AI 解读**。
前两者直接取自计算层、**AI 不可修改**；AI 只负责填 `interpretation`。三者在数据层就是分开的字段。

因此前端**不得**把 `facts` 拼进 AI 文本里渲染 —— 那等于在界面层把"防幻觉污染"的机制拆掉。
同理：**不确定性清单不得折叠、不得改写**（它是用户判断结论可靠性的唯一依据），
**免责声明固定在标签之外**（跟着标签切换而消失等于没附）。

这三条都写在 `app/report/[sessionId].tsx` 与 `apps/mobile/README.md` §五。

### ⑥ 不许为"看起来合理"而伪造 → 视觉层用同一条规则

RULE-008 原本针对数据，但它在**视觉层**同样成立，而且有一个极好的例子：

`src/lib/dialStyle.ts` 的注释里明确写着 ——

> 🔴 **本文件只放"画得出来"的层，不放"编得出来的层"。**
> 真实罗盘还有七十二龙、六十四卦、二十八宿等环带，但仓库里**没有这些层的数据表**。
> 宁可不画，也不为了"看着像真罗盘"而凭空编造术数内容。

于是盘面只画有数据支撑的六类环带。**这是一个可以拿来做正面案例的设计取舍**：
"视觉完整度"让位于"不编造"。

## 2. 设计系统

### 2.1 色彩：五色 + 派生中性阶 + 深色仪器域

五色不是挑出来的，是从界面演示图**逐像素中位数取样**实测的（`y=120`，五个圆形色块圆心 x = 731/768/804/840/877）。
它们随后被验证确实是界面在用的颜色（按像素命中数统计），所以这个色板可以当基线用 `[已确认]`。

| Token | 色值 | 语义 | 用途 |
|---|---|---|---|
| `brand.primary` | `#013A6C` | 主色 · 深蓝 | 主按钮、标题、选中态、导航激活 |
| `brand.gold` | `#DAB37D` | 金 · 辅色 | 强调描边、勋章、等级、点缀 |
| `brand.sand` | `#E5D7C7` | 米 · 底色 | 卡片底、分区背景、留白填充 |
| `brand.jade` | `#3C7066` | 墨绿 · 辅色 | 传统纹样、辅助图形、次强调 |
| `brand.cinnabar` | `#B93E35` | 朱红 · 强调 | 印章、吉凶提示、关键警示 |

两个值得注意的设计推理（都写在 `tokens.ts` 的注释里）：

- **中性阶是"派生"的，不是纯灰。** 五色里没有中性色，而界面的 90% 面积其实是文字、分隔线、卡片底。
  以 `sand(#E5D7C7)` 为暖调基准派生整条灰阶，整屏色温才统一 —— 直接用纯灰会显脏。
- **朱红不做导航选中色。** 它在本产品里承载"印章 / 焦点"语义，做成常规选中态会削弱它的表意。
  所以底栏激活色用主色（深蓝），未激活用 `muted`。这类"语义优先于美观"的取舍在本项目里是常态。

**深色仪器域（`instrument`）** —— 仅用于罗盘域：

| Token | 色值 | 用途 |
|---|---|---|
| `bg` | `#0A1626` | 页面最底层（深藏青） |
| `surface` | `#12223A` | 卡片 / 分区 |
| `border` | `#24395C` | 细边框 |
| `dialBody` | `#0D1B2E` | 罗盘盘体底色（深墨青，区别于页面底） |
| `needle` | `#E05548` | 磁针红（与朱红同源，深底上略提亮） |
| `text` | `#F2EDE4` | 主文字（暖白，不用纯白） |

> ⚠️ **双轨是当前状态，不是最终态 `[待验证]`。** 是否全局深色化，要等**真机走查**
> 看完两轨的实际观感后才能定。不要把"两套配色并存"读成设计不统一。
>
> **两轨的实际边界**（按 `instrument` 在源码里的引用逐页统计 `[已确认]`）：
>
> | 深色仪器风（6 页） | 浅色暖调（其余 11 页） |
> |---|---|
> | 罗盘首页 · 测盘 · 手动调节 · 传感器测量 · 罗盘校准 · 我的罗盘 | 罗盘识向 · 确认坐向 · 会话详情 · AI 报告 · 命盘 · 占测 · 黄历择日 · 三式排盘 · 历史 · 我的 · 分析 |
>
> 分界线不是"是不是罗盘"，而是**"是不是在测量 / 操作罗盘"**：
> 拍摄、对盘、看传感器读数是仪器操作，走深色；
> 确认、阅读报告、看命盘是信息阅读，走浅色暖调。
> 注意 `CompassDial` 因此备有 `DIAL_LIGHT` / `DIAL_DARK` 两套盘面调色板 ——
> **两轨共用同一套几何**（`dialLayout` / `dialStyle`），只有配色不同。

### 2.2 排版

字体走系统默认（**未内嵌自定义字体**）—— 这是个有意的决定：中文字体文件动辄 5–10 MB，
打进 APK 会让包体积翻好几倍，而 iOS 的苹方 / Android 的思源黑体本身就已是高质量中文字体。
所以本项目的排版功夫全花在**阶梯与字距**上，而不是换字体。

字号阶梯 **8 档**（`xs 11` → `display 32` → `metric 40`），行高按约 1.5 倍配套
（中文比拉丁文需要更宽的行距；`metric` 例外，它是单行读数，行高给 46 而不是 60）。
字重 **5 档**（400/500/600/700/800）。**字距 5 档**
（`tighter -0.8 / tight -0.4 / normal 0 / wide 0.6 / wider 1.2`）。

**为什么中文特别需要字距阶梯**：拉丁文有大小写，层级可以靠 Case 表达；
中文没有，**层级只能靠"字号 × 字重 × 字距"三件套**——少一件就会出现
"字号变了但看起来还是同一层"。规则是：大字用负字距（40px 上不收紧会"漏风"），
小标签用正字距（11px 上不加宽会挤成一团）。

`AppText` 上有一组**语义化角色**，读页面时按这四层对照即可：

| 层 | 角色 | 记号 |
|---|---|---|
| 1 | 页面主标题 | `xl 20` / `bold` / `text` / `tight` |
| 2 | 分区标题、卡片标题（`SectionTitle`） | `md 15` / `semibold` / `text` / `wide` |
| 3 | 正文 | `md 15` / `regular` / `text` |
| 4 | 辅助说明、注释（`Label`） | `xs 11` / `medium` / `textSecondary` / `wider` |
| 特 | 仪表读数（`Metric`），**一屏一个** | `metric 40` / `heavy` / 域强调色 / `tighter` / 等宽数字 |

> ⚠️ **2026-09-18 修正了一处层级倒挂**：分区标题原是 `sm 13` + `textSecondary`，
> 比它自己的正文（`md 15` + `text`）**更小更淡** —— 卡片标题读起来比卡片内容次要。
> 19 个页面全中，且不影响任何测试。现在的规则是：
> **同一容器内，标题的字号不得小于正文，颜色不得比正文更淡。**
> 这条值得在分析其它页面时用作对照（`05-almanac` / `18-session` 的变化最能看出差别）。
>
> 另外：凡"数值会原地变化"的地方都用等宽数字（`AppText numeric` 或 `Metric`）。
> 比例数字下 "1" 比 "8" 窄，读数一跳整行长度就跳 —— 传感器页每秒刷几次，抖动会被读成"界面在闪"。

### 2.3 间距、圆角、阴影

- **间距严格 8pt 栅格**：`0/4/8/12/16/20/24/32/40/48`（`space[1..12]`）。
- **圆角六档**：`xs 4 / sm 6 / md 10 / lg 14 / xl 20 / pill 999`。
  用法有层级：外层容器 `lg`、内嵌图形 `sm`、按钮 `md`、标签 `pill`（**内紧外松**）。
- **阴影三档，同时给 iOS `shadow*` 与 Android `elevation`**
  （只写一套会在另一端静默失效）：`card`（静置，范围大而极淡）／
  `raised`（浮起）／`pressed`（**按下时收紧** = 物理下沉）。
  阴影色统一带底色暖调 `#2C2416`，不用纯黑 —— 纯黑投在暖白纸上会发脏。
- ⚠️ **深色仪器域不用投影**。深底上的投影看不见，只会让边缘发脏；
  深色页的层级靠「底差 + 1px 描边」表达（见 `Panel`）。
  这正是深色页当初**无法复用浅色 `Card`** 的真正原因 —— 不只是色值不同。
- 布局常量：页面横向留白 `16`，底栏可见高 `58`（不含安全区），内容最大宽 `560`。

### 2.4 交互常量（`interaction`）

按压反馈只允许从 `theme/tokens` 的 `interaction` 取值，实现只有一份（`usePressScale`）。

- `pressedScale 0.985` —— 缩放会把**文字和图标一起带走**，读起来是"整块被按下去"；
  只改底色的话图标纹丝不动，看着像背景闪了一下。
- `pressDuration 150ms` —— 按下即刻有回应，同时不拖沓。
- `minTouchTarget 44` —— 视觉可以更小，但必须用 `hitSlop` 补足。

> ⚠️ **2026-09-18 之前这里有五种写法并存**：`Button` 用 `opacity 0.86`、
> 首页「去测盘」换底色、首页「已保存 N 个盘面」**完全没有反馈**、
> `Chip` 用 `opacity 0.7`、`SegmentedTabs` **也完全没有**。
> 同一个手势在不同地方给出不同回应，用户读到的不是"风格差异"而是"有的地方坏了"——
> **而它不会在任何一个测试里失败**。
>
> 实现上刻意用 RN core `Animated`（`useNativeDriver`，非 web 平台）+ `transform`，
> **没有引入 `react-native-reanimated`** —— 引它要动 babel 配置与新架构开关，
> 成本远大于一个 120ms 缩放反馈的收益。要换弹簧物理时只需改 `usePressScale.ts` 一个文件。

### 2.5 界面上的九条硬约束

摘自 `apps/mobile/README.md` §五 —— 这些不是风格偏好，是产品前提的落地要求：

1. 不给角度输入框（见 §1③）
2. 向山不可独立选择（见 §1③）
3. **不显示"AI 正在思考"** —— 识别过程要展示**可验证的步骤**（质检→边界→天池→透视→二十四山→坐向→分金→解读）。
   客户端拿不到服务端中间态，所以步骤状态**只由真实返回驱动，不按定时器自嗨式推进** —— 那是在编造过程。
4. `null` 一律渲染为「未定」，绝不留空
5. 报告三标签内容**物理分离**，不合并渲染
6. 不确定性清单不得折叠或改写
7. 免责声明固定在标签之外
8. 组件内不得出现硬编码色值
9. **文案里不得出现 Markdown 标记** —— RN 的 `<Text>` 把 children 当**纯文本**渲染，
   `**强调**` 会原样显示成两个星号。这一条是本导出包**自己复盘出来的教训**：
   仓库里曾同时存在 63 对标记（其中 `src/content/help.ts` 占 53 对 = 每页「讲解」抽屉的全部正文），
   而 `tsc` / 单元测试 / 离线快照三处防线**全都看不见它** ——
   快照只回传**布局诊断**（溢出量、JS 错误），不核对正文里有没有多余字符。

> 第 3 条有个值得注意的推论：`StepList.tsx` 里有一套 `SCAN_STEPS`，
> 但它只负责**画**步骤；哪一步处于什么状态由真实返回值决定。这类"界面不编造过程"的约束，
> 在分析交互设计时是个高信号点。
>
> 第 9 条的推论：**"这个界面看起来对"与"这个界面读起来对"是两件事**。
> 布局诊断能证明前者，后者要靠对**文本内容本身**的断言（`tests/mobile/test_ui_copy_plain_text.py`）。
> 分析这套界面时，凡是"值会进入界面"的地方，都值得问一句：它有没有被验证过**内容**，而不只是**位置**。

## 3. 信息架构与页面地图

### 3.1 底栏：罗盘 ｜ 测盘 ｜ 分析 ｜ 历史 ｜ 我的

**五个位置，顺序不可调换**（`app/(tabs)/_layout.tsx`）。

⚠️ **这里有一处文档漂移，分析时请注意**：
项目《产品基线规范》（本包 `references/` 里那份）裁定的是
「罗盘 ｜ 命盘 ｜ 占测 ｜ 历史 ｜ 我的」。V2 改版后实际实现为
「罗盘 ｜ **测盘** ｜ **分析** ｜ 历史 ｜ 我的」—— 命盘与占测**并入了「分析」内页**。

改版的理由写在 `_layout.tsx` 注释里：底栏是给**高频动作**留的位置，
测盘（拍盘/对盘/存盘）天天要做，而排盘是"想起来才做一次"的；
四个低频谱术式摊在底栏会把高频的测盘挤掉。术式入口一个都没少，只是搬进了内页。

## 4. 组件库（14 个）

**三个表面原语，别再多造第四个** —— 这是 2026-09-18 补上的规则，
也是本次改动最值得看的一处结构性修正：

| 原语 | 域 | 用途 |
|---|---|---|
| `Card` | 浅色（纸面） | 命盘 / 占测 / 历史 / 我的 等阅读型页面。含 `variant: default \| quiet` |
| `Panel` | **深色（仪器）** | 首页 / 测盘 / 手动调节 / 传感器 / 校准 / 我的罗盘 |
| `PressableCard` / `PressablePanel` | 两域各一 | 整卡可点（进详情、跳转），自带统一按压反馈 |

> ⚠️ **`Panel` 是补上来的**：原先只有浅色 `Card`，深色页用不了，
> 于是 **6 个深色页各自把「surface 底 + 1px 边框 + `radius.lg` + padding」抄了一遍**
> （同一组样式重复 17 次，`instrument.surface` 出现在 7 个文件 29 处）。
> 散落的不是色值而是**样式组合**，所以 tsc、lint、任何测试**都不会报错** ——
> 只有在改圆角 / 改边框色时才会发现"改了一页，另外五页没跟上"。
>
> 这也解释了为什么 `calibrate.tsx`（深色页）至今用的是**浅色 `Card`**（白卡浮在近黑底上）：
> 当时没有深色原语可用。渲染出来是"白色读数铭牌压在深色控制台上"，
> 观感尚可但**与同域另外五页不一致** —— 这是**已知的、待裁定的一致性疑点**，不是刻意设计。

| 组件 | 职责 | 关键约定 |
|---|---|---|
| `AppText` | 排版基元 | 尺寸/字重/颜色只接受 token 的键名，从类型层杜绝散落字号；`track` 字距档、`numeric` 等宽数字 |
| `Metric` / `Label` | 仪表读数 / 小标签 | 读数**一屏一个**；标签自带正字距 |
| `Screen` | 页面容器 | 安全区 + 背景 + 布局约束；`Centered` 用于居中态 |
| `Card` | 浅色卡片，含 `Button` / `EmptyState` / `KeyValueRow` | 空态组件强制给出可操作提示，而不是只写"暂无数据" |
| `Panel` | **深色卡片**（仪器域） | 不用投影，靠底差 + 描边分层 |
| `usePressScale` | **全 App 唯一的按压反馈** | 见 §2.4；`transform: scale` 走原生线程 |
| `Chip` / `Tag` | 可选标签 / 吉凶标记 | `Tag` 有 good/bad/neutral 三态 |
| `Banner` / `UncertaintyList` | 提示条 / 不确定性清单 | 清单**不折叠、不改写**；色值走 `tone` 三件套 |
| `SegmentedTabs` | 分段切换（泛型，键名受类型约束） | 报告三标签、扫描页双入口都用它 |
| `HelpButton` | 讲解入口 | **未登记的 topic 不渲染入口** —— 宁可没有，也不给一个点开是空的按钮 |
| `CompassDial` | 罗盘盘面仿真 | 见下方四条语义约定 |
| `CompassAdjuster` | 二十四山环形选择器 | 不给角度输入；向山跟随坐山 |
| `StepList` | 识别步骤 | 只由真实返回驱动，不做定时推进 |
| `DuanCard` | 断卦结论卡 | **中性结论不得上红/绿** |
| `FactList` | 盘面事实表 | `null` → 「未定」 |

### `CompassDial` 的四条语义约定

这个组件最容易"改错而不自知"，它的注释里列了四条硬约定：

1. **屏幕正上方恒为真北**，磁针不随盘面旋转（实物罗盘上转的是盘体，磁针始终指北；反过来画会让人以为罗盘坏了）。
2. **`rotation` 是盘体的旋转量**（顺时针为正）；盘面角 θ 的显示位置 = θ + rotation。
3. **坐山/向山/实测角都存"盘面角"，不存屏幕角** —— 旋转是视角，选择是事实。
   这样旋转盘面不会悄悄改变"用户选的是哪座山"。
4. **盘式（`style`）只影响画哪些层、每层多宽，不影响任何角度换算** —— 切盘式不该让"用户选的是午"变成别的山。

> 第 4 条是"几何是事实、配色是视角"这句话的具体含义。
> 盘面配色角色（红/蓝/墨）属**盘式流派**（各版罗盘分色不同），仅影响视觉识别，不参与任何术数计算 `[待验证]`。

### `DuanCard` 的配色规则

断卦结论里的「身强 / 身弱」是**状态**而不是**吉凶**，必须走中性色。
`verdictTone` 的白名单只认「偏吉 / 偏凶」，把「身弱」画成红色即属违规（RULE-008 的界面版）。
这是一条"看起来吹毛求疵、实际防止语义污染"的规则，很能代表本项目的设计取向。

## 5. 数据从哪来

界面上的每个数字都来自后端 HTTP 接口。`08-api-contract.md` 里的 `types.ts` 与后端 schema 一一对应，
覆盖罗盘识别、八字、六爻、灵签、命名、黄历、择日、断卦、奇门、六壬、太乙共十余个领域。

三件与分析相关的事：

- **客户端不持有任何模型密钥。** provider 的能力与可用性一律从 `/api/v1/meta/ai-providers` 读服务端状态，客户端只负责展示。
- **"无数据"是一等状态**，不是异常路径。见 §1②。
- **识别原件不被用户确认覆盖。** 会话详情页会同时给出"机器当时看到什么"（识别原件，只读）与"你最终怎么定"（确认结果），
  两者是独立可核对的记录。`18-session.png` 的正文里能读到这段文案。

## 6. 已知限制 —— 分析前请先读这一节

> 这一节存在的意义：避免你基于一份**看起来完整**的材料，得出一个**实际上还没被验证过**的结论。

### 6.1 快照不是真机截图

21 张快照由 `expo export --platform web` 的产物在 Chrome 里按手机视口（390×844 @2x）渲染，

所以布局、折行、配色、空态这些结论是可靠的；

但以下**不能**由这些快照得出：真机字体渲染差异、原生控件观感、安全区实际留白、
键盘遮挡、滚动手感、以及任何传感器/相机的真实行为。`[已确认]`

### 6.2 真机 UI 走查从未做过

这是本项目当前**最高优先级的未验证项**。所有界面验证都止步于"离线渲染 + 类型检查 + 打包验证"，
没有任何一次是在真实设备上逐页走过的。`[已确认]`

### 6.3 报告页的三标签内容态没有快照

`19-report.png` 是**报告页的空态**（未生成报告时的表单：问题类别、模型偏好、离线模式开关），
它恰好演示了"无数据是一等状态"这条规则。
但报告页真正的核心 —— **三标签 + 不确定性清单 + 免责声明**的完整形态 —— 需要先生成一份报告才能看到，
本包中**没有**这一状态的快照。不要把它当作"报告页已完整验证"。`[已确认]`

### 6.4 盘式的层宽比例是视觉拟定值

`src/lib/dialStyle.ts` 里各盘式的层数与层宽比例，是按"层数越多、每层越窄"的常见形制拟定的，
真实罗盘各版尺寸不一。它只影响观感，不参与任何术数计算。`[待验证]`

### 6.5 两处已过时 / 与规范不一致的地方

- `apps/mobile/README.md` 的目录结构章节仍是底栏改版前的旧结构（见 §3.1）。

### 6.6 快照的会话三页依赖运行时数据

## 8. 重新导出

源码变更后（或在另一台机器上），在本仓库根目录执行：

```bash
# 环境变量：$PY = 托管 venv 的 python.exe
"$PY" scripts/export_ui_design.py                 # 生成到 dist/ui-design-export/
"$PY" scripts/export_ui_design.py --zip           # 同时打包 zip
```

脚本会先做**归档完整性自检**：`app/` 与 `src/` 下有任何一个源码文件未被任何一卷收录，
就直接报错退出（防止导出包静默缺页）。

刷新快照需要三步（需要后端在跑）：

```bash
# 1) 导出 expo web 产物（输出到系统 Temp，避开本机 safe-delete 的批量删除守卫）
"$PY" scripts/ui_render/preview_server.py "$TEMP/xp-web" 8955 &

# 2) 渲染全部页面
node scripts/ui_render/render_pages.mjs "<chrome.exe 路径>" docs/ui-render http://127.0.0.1:8955

# 3) 会话三页需要真实 sessionId（不传就跳过这三页）
XP_SESSION_ID=<会话 ID> node scripts/ui_render/render_pages.mjs ... 17-confirm,18-session,19-report
```

会话 ID 可从 `GET /api/v1/sessions` 取。

# 外部项目评估 — suanming-mcp（玄机阁）

> **被评估对象**：<https://github.com/Enoch666/suanming-mcp>
> **版本指纹**：commit `f08ec272b6928af8faa79300f50b4d740ffbbd1f`（2026-07-20），package version `1.0.0`
> **评估时间**：2026-09-17
> **评估方法**：克隆源码 → 逐文件读实现 → **独立复算**（不依赖原项目测试，因其无测试）→ 与玄盘 `fortune-core` 交叉比对
> **结论可信度**：本文所有「错」的判定均附可复现的复算脚本与真实输出，标 `[已实测]`；仅有推断的部分标 `[推测]`

---

## 0. 一句话结论

**它是一个包装精美、娱乐定位明确的 MCP 演示项目，不是一个可用的术数计算内核。**

- 架构与打包方式（MCP Server + Agent Skill + HTML 报告）**值得借鉴** `[已实测]`
- 术数计算层**不可信、不可移植**：六爻卦名映射 63/64 错配，八字月柱 10/10 全错、年柱靠公历年蒙对 6/10 `[已实测]`
- 它的问题类型和玄盘项目 RULE-001 想防的**是同一类**——「看起来正常但其实是错的输出」，即假阳性

## 1. 它到底是什么

| 维度 | 事实 |
|---|---|
| 语言/技术栈 | TypeScript 5.3 + `@modelcontextprotocol/sdk`，**零其他依赖** |
| 代码体量 | `src/` 共 **1851 行**（含数据表），12 个 `.ts` 文件 |
| 数据体量 | 64 卦表 + **100 签**（自撰）+ **254 字**用字/笔画表 |
| 测试 | **0 个**。`package.json` 无 test 脚本，无 `__tests__`、无 CI 配置 `[已实测]` |
| 输出形态 | 每次调用写一个 HTML 到 `~/.suanming/`，并 `open`/`start` 唤起浏览器 |
| MCP 返回 | 仅 `content: [{type:"text", text: "摘要…\\n📄 页面路径"}]`，**无 `structuredContent`** |
| LICENSE | MIT |

### 1.1 三个结构性判断

**① 计算层没有「历法」这个概念**

`bazi.ts` 全文 157 行，**不依赖任何万年历/节气库**。年/月/日/时柱全部由整数取模算出（见 §3.2）。
这意味着它的八字**不可能**处理节气、真太阳时、农历、时区——而这些是八字的**定义域前提**，不是优化项。

**② 输出不可被下游消费**

MCP 只回一段自然语言摘要 + 文件路径。Agent 拿不到 `pillars`、`gua`、`score` 这类结构化字段，
因此**无法做二次计算**（例如「用这个八字去排大运」「用这个卦去装六亲」）。
它是一次性的「看图工具」，不是「取数服务」。

**③ 六爻用确定性哈希「起卦」，且这个选择本身不构成问题**

`liuyao.ts` 用 `hash(问题) + 年月日` 作种子驱动 LCG，同日同问题必得同卦。
这是**可辩护的设计**（可复现、不依赖随机源），玄盘 `fortune-core` 的 `liuyao.py` 是同一路线（随机源上移到调用方）。
**问题不在起卦，在起卦之后的映射（见 §3.1）。**

### 2.2 `fortune_liuyao` — 卦序映射与数据表不同源 🔴

**症状**：64 卦数据表按**周易通行卦序**（1 乾 2 坤 3 屯 4 蒙…64 未济）排列，
但查询用的 `linesToGuaNum()` 产生的是**二进制索引** `Σ lines[i] << i + 1`。两套序不兼容。

**复算**（`scripts/cmp_suanming_mcp.py` 检查 C1，复刻其算法并与其自带数据表交叉验证）：

```
检查 C1 · 六爻卦序映射自洽性（其数据表 vs 其查询算法）
==========================================================================
  解析到卦表条目：64
  自洽命中 1/64，错配 63/64
    乾为天(☰☰) -> 查到 火水未济
    坤为地(☷☷) -> 查到 乾为天
    水雷屯(☵☳) -> 查到 山风蛊
    山水蒙(☶☵) -> 查到 火地晋
    水天需(☵☰) -> 查到 地雷复
  反例：六爻全阳 → 应得「乾为天」，实际得「火水未济」
  反例：六爻全阴 → 应得「坤为地」，实际得「乾为天」
```

> 「自洽命中 1/64」的含义：把**每个卦自己的真实爻画**喂回它的查询函数，
> 只有 1 个卦能查回自己。这不是精度问题，是两张表根本不同源。

**含义**：这是**最严重的一类缺陷**。用户摇出六爻全阳（唯一确定的乾卦），拿到的却是「火水未济」和它的吉凶判词。
输出表面上完全正常（有卦名、有卦辞、有解读、有变爻标记），**没有任何机制能让用户察觉出错**。

对照：玄盘 `fortune-core/liuyao.py` 用显式二维表 `LIUSHISI_GUA[下卦][上卦]`，实测全阳→乾、全阴→坤 ✅

### 2.3 `fortune_bazi` — 年柱、月柱无节气概念 🔴

**根因（读源码即可确认）**：

```ts
getYearStem(year)  { return HEAVENLY_STEMS[(year - 4) % 10] }        // 直接用公历年，无立春切换
getMonthBranch(m)  { return EARTHLY_BRANCHES[(m + 1) % 12] }         // 直接用公历月，1月→寅
getMonthStem(yi,m) { const base = (yi*2) % 10; ... (base+m-1) % 10 } // 五虎遁起点少 +2
```

三条都是定义层面的错：年柱必须过**立春**切换，月柱必须按**十二节**（立春/惊蛰/清明…）划界，
月干五虎遁口诀「甲己之年丙作首」要求起点为 `(年干序 * 2 + 2) % 10`，源码少了恒定的 `+2`。

**复算**（`scripts/cmp_suanming_mcp.py` 检查 A：移植其算法 vs `fortune-core`（`lunar-python`），10 组样例 × 4 柱）：

```
检查 A · 八字四柱对照（suanming-mcp 算法 vs fortune-core / lunar-python）
==========================================================================
  1990-05-20 10:00   年柱   庚午      庚午      OK       README 示例
                     月柱   庚午      辛巳      错
                     日柱   乙酉      乙酉      OK
                     时柱   辛巳      辛巳      OK

  2000-01-01 08:00   年柱   庚辰      己卯      错        README 示例 · 立春前
                     月柱   丙寅      丙子      错
                     日柱   戊午      戊午      OK
                     时柱   丙辰      丙辰      OK

  1988-02-03 23:00   年柱   戊辰      丁卯      错        立春前 1 天 + 晚子时
                     月柱   癸卯      癸丑      错
                     日柱   戊子      戊子      OK
                     时柱   壬子      甲子      流派差异

  1990-02-04 10:00   年柱   庚午      己巳      错        立春当日
                     月柱   丁卯      丁丑      错
  ...
  （共 10 组，其余略）

  合计 40 项柱位
    年柱：真错 4/10  流派差异 0  🔴 系统性错误
    月柱：真错 10/10 流派差异 0  🔴 系统性错误
    日柱：真错 0/10  流派差异 0  ✅ 一致
    时柱：真错 0/10  流派差异 1  ⚪ 仅流派差异
```

**逐柱判读（这里要分清「真错」和「流派差异」，不能一刀切）**：

| 柱 | 结果 | 判读 |
|---|---|---|
| **月柱** | 10/10 错 | 🔴 **真错且必然错**。用公历月冒充节气月，加上海虎遁起点偏移，没有任何一组日期能对 |
| **年柱** | 4/10 错 | 🔴 **真错，错误集中在立春窗口**。1 月~2 月初出生者年柱必错（含 README 自己的示例） |
| **日柱** | 0/10 错 | ✅ 1900-01-01 基准取对了。但用 `new Date()` 本地时间做差，夏令时/跨时区会 ±1 天 `[推测]` |
| **时柱** | 真错 0，流派差异 1 | ⚪ **不算错，是流派差异**。差异仅出现在 23:00 晚子时，其处理（日柱算当天 + 时干用当天日干）是通行口径之一。但源码**未声明口径**，玄盘则显式暴露 `sect` 参数 |

**补充：源码里那句「今日运势」是纯装饰**

```ts
const luckSeed = year + month + day + today.getFullYear() + today.getMonth() + today.getDate();
const luckIndex = luckSeed % 5;   // 取 5 档「大吉/吉/平/小凶/凶」
```

这个值与命主的日主、喜用、五行**毫无关系**，只是个被日期锁定的伪随机数。
更严重的是：**它被放在「日主分析」紧后面**，视觉上像命理推演结果——典型的假阳性包装。

**同样缺失的还有**：大运、起运岁数、流年流月、十神、地支藏干、旺衰判定、格局、神煞、纳音、空亡、胎元、命宫。
「日主分析」只是 10 条固定文案查表。

对照：玄盘 `bazi` 走 `lunar-python`，并额外提供 `hour_pillar_by_rule` / `month_pillar_by_rule`
两条纯口诀函数做**交叉校验自证**（`verify_rule_consistency()`），输出 `十神/藏干/旺衰/喜忌/纳音/空亡/胎元/命宫`。

### 2.4 `fortune_name` / `fortune_mingming` — 笔画静默造假 🟠

**字库规模**（`scripts/cmp_suanming_mcp.py` 检查 C2）：

```
NAME_CHARS 起名用字库 = 145 条；STROKE_MAP 姓氏笔画表 = 109 条；合计 254
```

**未收录字符的处理方式**（`characters.ts` L194-202，源码原文）：

```ts
if (NAME_CHARS[char]) return NAME_CHARS[char].strokes;
if (STROKE_MAP[char]) return STROKE_MAP[char];
// 简单估算：CJK 统一汉字范围
const code = char.charCodeAt(0);
if (code >= 0x4E00 && code <= 0x9FFF) {
  return Math.max(1, Math.min(30, Math.floor((code - 0x4E00) / 500) + 4));
}
```

**它用 Unicode 码位反推笔画数**。抽查常用姓名汉字：

```
  字   康熙真值  程序取值  来源
  阿       8       30     ❌ Unicode 估算兜底
  玄       5       23     ❌ Unicode 估算兜底
  盘      15       24     ❌ Unicode 估算兜底
  王       4        5     表内(值不符)
  管      14       27     ❌ Unicode 估算兜底
  辉      15       30     ❌ Unicode 估算兜底
  娜      10       10     ❌ Unicode 估算兜底

  抽查 11 字：未收录走 Unicode 估算 = 6；表内但笔画不符 = 1
```

**含义**：对字库外的字，五格数理、81 数理吉凶、三才配置、综合评分**全部**基于虚构笔画。
「管」在项目自己的截图 `01-起名-管姓男孩.png` 里就出现了——按源码它算作 27 画（真值 14 画）。
**用户拿到的是一个 5 星好评的名字，而它建立在错笔画上。**

**另外，「外格」公式与通行算法不符**（复算）：

```
检查 B · 姓名五格公式（源码 vs 通行「外格 = 总格 − 人格 + 1」）
==========================================================================
  王小明 · 天格：源码=6   通行=6   一致
  王小明 · 人格：源码=16  通行=16  一致
  王小明 · 地格：源码=19  通行=19  一致
  王小明 · 外格：源码=13  通行=9   ❌ 不一致
  王小明 · 总格：源码=24  通行=24  一致
```

源码 `wai = s3 ? s1 + s3 : s1 + 1`（姓 + 名末字），通行算法 `外格 = 总格 − 人格 + 1`（= 名末字 + 1）。
复姓（欧阳/司马）、单姓单名也未做分支处理。

#### 📌 这一处最能说明两个项目的分野

两个项目的笔画表**都缺字**，但缺字时的行为完全相反：

| | suanming-mcp | 玄盘 `fortune-core` |
|---|---|---|
| 笔画表条目 | **254**（145 起名用字 + 109 姓氏） | **502**（`data/kangxi_strokes.json`，`verified: false`） |
| 缺字时 | `Math.floor((code - 0x4E00) / 500) + 4` —— **按 Unicode 码位编一个数** | 抛 `DomainDataMissingError`，**列出缺字并提示补表** |
| 用户看到 | 一个 5 星好评的名字 | 「缺少以下字的康熙笔画：玄盘。请通过 strokes 参数显式提供，或补充 data/kangxi_strokes.json」 |

实测对照（同一个字「管」）：

```
suanming-mcp：管 -> 27 画（Unicode 估算）   项目自己的截图 01-起名-管姓男孩.png 就用这个字
玄盘        ：管 -> 14 画（表内，与康熙字典一致）
```

```
# 玄盘实测
>>> analyze_name('玄盘')
DomainDataMissingError: 缺少以下字的康熙笔画：玄盘。请通过 strokes 参数显式提供，
                        或补充 data/kangxi_strokes.json（该表当前为部分覆盖）。
```

**这正是 RULE-001 与「假阳性」问题的教科书级对照**：
玄盘的 502 字表同样不完整（`verified: false`，尚未与权威字书逐条比对），
但它**拒绝在数据缺失时给出一个看起来正常的答案**。
`suanming-mcp` 选择静默编造——用户拿到的是一个**无法分辨真假的评分**。

> ⚠️ 顺带暴露的自身问题：玄盘笔画表连「玄」「盘」都没有，这是 `naming.py` 当前的**真实缺口**，
> 见 §5.2 第 5 条。它不影响正确性（会报错），但影响可用性。

### 2.5 `fortune_qian` — 100 签为自撰签谱 🟡

**取证**：项目第 1 签是「一轮明月照清波，万里无云气象和。自有贵人相扶助，诸般顺遂不须多。」
而观音灵签第 1 签（《观音一百签》传统文本，公版）为：

> 开天辟地作良缘，吉日良时万物全。若得此签非小可，人行忠正帝王宣。

签名相同（都叫「第1签」），**内容毫无关系**。签诗等级分布也异常偏吉：

```
上上 16 | 上 20 | 中上 20 | 中 20 | 中下 15 | 下 10
```

传统观音灵签的分布大致为 上上 3 / 上吉 13 / 中吉 30 / 中平 32 / 中下 12 / 下下 10——**吉签占比被显著放大**。

**判读**：项目 README 与 SKILL.md 均未声称签文出自某传世签谱，从「程序员整活」定位看**不算欺诈**。
但工具名 `fortune_qian` 与描述「从灵签筒中抽取一支签」会让用户默认其为传统签谱——
**这是一处措辞与实现不匹配**，需要在使用时明确标注。

对照：玄盘 `fortune-core/qian.py` 的做法更保守——模块 docstring 显式声明**不分发任何传世签文全文**，
`data/qian/demo_guanyin.json` 带 `demo: true` 元数据，并说明「把合法签库 JSON 放进 `data/qian/` 即可启用」。
**两种处理方式的高下，正好对应 RULE-001 的核心关切。**

## 3. 真正值得借鉴的三件事

> 这段才是本次评估对玄盘的**正收益**。方法论清楚标明是「借鉴架构」，不涉及任何计算逻辑。

### 3.1 MCP 暴露层：把内核包成 Agent 可调用的工具

它证明了**一条低成本路径**：`@modelcontextprotocol/sdk` + `StdioServerTransport`，**192 行**即可完成
「注册工具 → 校验参数 → 调内核 → 回结果」。玄盘 `fortune-core` 已经是纯函数 + 领域数据的形态，
比它更适合做 MCP 暴露（我们有结构化输出，它没有）。

**但必须修掉它的两个反模式**：
- ❌ 只回自然语言摘要 → 玄盘应回 **`structuredContent`**（FACT / TRADITION 两层已是现成 JSON）
- ❌ 每次调用 `openBrowser()` 强行弹浏览器 → 副作用必须由调用方决定

### 3.2 `SKILL.md` 打包：一个仓库同时是 MCP Server 和 Agent Skill

它的 `SKILL.md`（frontmatter 带 `name` / `description` / `metadata.topics`）让同一份代码
既被 Claude Code 等 MCP 客户端调用，又被 Agent 当 skill 加载。**这是值得抄的打包范式**，
玄盘的 `docs/` 里已有多份对外文档，缺的正是这一层「Agent 入口」。

### 3.3 HTML 报告渲染：水墨视觉是真实资产

`render/template.ts`（305 行，全项目最大文件）用纯 CSS 做出了宣纸纹理、毛笔标题、朱砂印章、竖排签文。
玄盘移动端的三层报告（盘面事实 / 传统分析 / AI 解读）若要出**可分享的 HTML 版**，
这套配色与版式可直接参考（注意其色板是**水墨暖调**，与玄盘演示图色板 `#013A6C`/`#DAB37D` 不同体系，不可混用）。

### 4.2 缺口的三个层次

**第一层：它做到了「有输出」，但没做到「输出为真」**
`fortune_liuyao`（卦序错）、`fortune_bazi`（年月柱错）、`fortune_name`（笔画造假）都在这一层。
**这不是「完成了一部分」，这是「完成的部分里有三件是坏的」。**

**第二层：整个「装卦/起运」中间层是空的**
六爻起完卦之后要**装卦**（纳甲、六亲、世应、六神）才能断卦；八字排完盘之后要**起运**（大运、流年）才能论命。
两个项目**都停在「排盘/起卦」这一步**。这一层才是术数的技术难点所在。

**第三层：三式（奇门遁甲 / 大六壬 / 太乙神数）完全空白**
这是传统术数里算法复杂度最高、也最需要「确定性内核」的部分——**恰好是玄盘 RULE-001 最该吃下的领域**。
目前没有任何开源 MCP 项目做这个 `[推测]`，是差异化机会。

## 6. 复现指引

  scripts/cmp_suanming_mcp.py --repo "C:/Users/anyong/AppData/Local/Temp/suanming-mcp"

| 检查 | 内容 | 是否依赖外部仓库 |

1. **产品方向成立，工程原则正确。** 核心是「罗盘数字化」，而非「AI 算命」。材料中反复强调的 `AI 负责看/理解/解释，代码负责算/校验/映射` 是本项目最有价值的资产 `[已确认]`。

### 2.5 ⚠️ 演示图八字排盘数据错误（代码实算）

演示图 4「八字排盘」展示：出生 `1981-09-14 08:00`，男，湖北 →

| 项 | 演示图 | 实算结果 | 判定 |
|---|---|---|---|
| 年柱 | 辛酉 | 辛酉 | ✅ |
| 月柱 | 丁酉 | 丁酉 | ✅ |
| **日柱** | **辛丑** | **乙未** | ❌ |
| **时柱** | **甲辰** | **庚辰** | ❌ |
| **日主** | **辛金** | **乙（木）** | ❌ |

**两条独立证据链**（详见附录 A）：

1. **纯规则自洽性**（不依赖任何数据库）：时柱由日干推出，口诀「丙辛从戊起」——辛日子时戊子，顺推至辰时应为 **壬辰**。因此演示图自身就是矛盾的：**它标称日主为辛，却给出甲辰时柱**。
2. **双源计算**：`lunar-python` 与「标准儒略日公式 + 偏移 k=49」两条独立路径给出**完全相同**的结果 `乙未日 / 乙木日主 / 庚辰时`，且 `k=49` 在 4 个测试日期上恒定，并被 `2000-01-01 = 戊午日` 这一公认锚点验证。

**裁定**：`[已确认]` 演示图数据为错误数据，**不得作为实现基准**。此案例恰好构成对 RULE-001（确定性计算必须由代码完成）的最佳注脚：**人工编造的术数数据，会以肉眼无法识别的方式出错**——连演示图都没能幸免。

## 3. 目标架构（确认版）

### 3.1 主链路

```text
Camera → Vision → Human Confirm → Fortune Core → Fortune Context → AI Router → Report → Multi-turn
```

### 3.2 分层职责

| 层 | 职责 | 关键约束 |
|---|---|---|
| 采集层 | 拍照、质量检测、透视校正、ROI 裁剪 | 客户端预处理器化，降低上传体积与 Vision 成本 |
| 识别层 | 罗盘 → 结构化 JSON | **不确定必须返回 null**（RULE-003） |
| **计算层** | 二十四山 / 坐向 / 分金 / 八字 / 五行 / 六爻 等 | **唯一真源，确定性，禁 LLM 介入** |
| 上下文层 | 组装 `FortuneContext` | AI 只见结构化数据，不见原始输入 |
| 解释层 | AI Router + Provider 抽象 | 只能解释，不能修改任何计算值 |
| 接入层 | REST API / MCP | APP、MCP、未来 Agent 共享同一内核 |

**架构核心价值**：`Fortune Core` 是被 APP / API / MCP / Agent 共享的**唯一计算内核**，不是为某个端写的代码。

### Phase 0 — 计算内核（当前推荐起点）

**交付物**：`packages/fortune-core`

- 二十四山数据模型（唯一标准表，作为**领域配置**而非散落在 UI/Prompt）
- 坐山 / 向山模型 + 几何关系校验（坐山≠向山、应处相对方位）
- 角度 ↔ 二十四山映射

- 完整单元测试

**Gate 0 验收**：`pytest` 全绿；核心算法测试覆盖率达标；**零 LLM 参与计算**。

### Phase 1 — 罗盘识别 Demo

**这是全项目最关键的一步，也是最大不确定性所在。**

- 拍照 → 客户端预处理（清晰度/反光/透视/裁剪）
- Vision Provider 抽象 + 至少 1 个实现
- 输出结构化 JSON（含 `confidence` 与 `needs_user_confirmation`）
- 人工确认 / 手动修正（二十四山环形选择器）

**Gate 1 验收**（直接沿用材料 A §50 的判据）：

> **普通用户拿手机拍一张真实罗盘照片，系统能否稳定识别鱼丝线对应的二十四山，并让用户在 3 秒内确认。**

**⚠️ 此 Gate 不通过，则后续全部设计需重新评估。** 建议尽早用最小成本证伪。

`FortuneContext` → LLM → 三层结构化报告（盘面事实 / 传统分析 / AI 解读）。含 AI 幻觉防护与不确定性标注。

## 6. 网络线路策略

材料 B §13–§19 将「网络线路」定位为 **AI 服务连接线路**，而非代理工具。这个定位是正确且必要的。策略要点：

1. **优先国内直连**：DeepSeek / Qwen / 智谱 / 豆包 作为**默认线路**，覆盖绝大多数场景，无跨境链路依赖。
2. **官方 API Gateway 模式**：模型调用统一走自建 Gateway（鉴权 / 限流 / Router / 成本统计），**API Key 永不进入客户端**（材料 B §27）。
3. **合规前提**：材料 B §16 已明确「线路、API 使用和服务部署需符合当地法律法规及模型服务商条款」。落地时必须遵守该前提 `[已确认]`。
4. **故障降级**：主模型失败 → 自动切换备用；**但模型切换绝不能改变 Fortune Core 的计算结果**（材料 B §21–§22）。
5. **对用户隐藏复杂度**：普通用户只见「已连接 / 延迟 / 自动选择」，技术参数收进「高级网络设置」。

### A.3 交叉验证

**路径一：lunar-python** → `乙未日 / 乙木 / 庚辰时`

**路径二：标准儒略日公式 + 恒定偏移**

| 日期 | JDN | 日柱 | 序号 | 偏移 k |
|---|---|---|---|---|
| 1981-09-14 | 2444862 | 乙未 | 31 | **49** |
| 2000-01-01 | 2451545 | 戊午 | 54 | **49** |
| 2024-02-10 | 2460351 | 甲辰 | 40 | **49** |
| 1990-05-20 | 2448032 | 乙酉 | 21 | **49** |

`k ≡ 49 (mod 60)` 在四个日期上**完全恒定** → lunar-python 采用标准 JDN 线性映射；且 `2000-01-01 = 戊午日` 为公认锚点 → 结果可信 `[已确认]`。

**路径三：纯干支规则自洽性（不依赖任何库）**

| | 日干 | 辰时应有 | 自洽 |
|---|---|---|---|
| 演示图 | 辛 | **壬辰** | ❌ 实为「甲辰」 |
| lunar-python | 乙 | **庚辰** | ✅ 实为「庚辰」 |

口诀依据：「丙辛从戊起」（辛日子时戊子）、「乙庚丙作初」（乙日子时丙子）。

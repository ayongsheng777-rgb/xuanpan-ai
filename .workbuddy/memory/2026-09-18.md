  v4（旧）**60 处**与中文相邻的裸星号 → v5（新）**0 处**；抽查 3 条已修文案均在包内

### 本轮踩到的三个新坑

1. 🔴 **`Path.write_text()` 在 Windows 上会把 LF 改成 CRLF** —— 用 Python 批量改源码时；
   `newline=None`（默认）写入时会把 `\n` 翻译成 `os.linesep`。本仓库 `.gitattributes`
   写着 `*.ts/tsx text eol=lf`，于是**仓库存储层看到的是规范化后的 LF，`git diff` 完全不显示这件事**
   （只在输出里留一句 `CRLF will be replaced by LF` 的告警），但工作区 5 个文件的 582/386/291/665/1009
   处行尾已被换掉。修法：批量改源码的脚本一律写 `write_text(..., newline='\n')`，或改完用二进制
   `read_bytes().replace(b'\r\n', b'\n')` 复核。**判据：改完立刻数 CRLF 个数，不要只看 git diff。**
2. 🔴 **`git commit -m "...`反引号`..."` 会被 bash 当命令替换吃掉** —— 提交说明里想写行内代码时；
   反引号内容是**被执行**而不是被记录，命令失败也只落到 stderr，commit 照样成功，
   于是说明里静默少掉一段（本次「只删 这 2 个字符」缺了 `**`，且多打一行 `AGENTS.md: command not found`）。
   修法：**含反引号的提交说明一律走 `git commit -F <文件>`**，用 Write 工具写文件、不经 shell 拼接。
3. 🔴 **守卫自己会坏，而且坏法是"永远通过"** —— 写静态扫描类测试时；
   第一版幂运算符判据用了 `[\w\)\]]\s*\*\*\s*[\w\(\[]`，而 **Python 的 `\w` 包含 CJK**，
   于是「程序**不会**替你摇」被判成幂运算符整段跳过。中文正是本项目正文语种 ——
   症状是**句中的标记被静默漏掉**、只有行首的能报出来，最坏情况是守卫全绿而缺陷全在。
   修法：显式写 ASCII 字符类 `[A-Za-z0-9_]`；并给守卫本身写两条"守卫的守卫"断言
   （该报的报 / 不该报的不报 / 剥注释不剥过头）。**这次正是这两条断言当场抓到了它自己。**

**教训（对"验证"这件事）**：源码改了 ≠ 产物改了。查产物时中文全是 `\uXXXX` 转义，
直接 grep 中文会得到**假阴性**（第一次 grep 就骗到我了：显示"已无星号"，实际是因为压根匹配不到中文）。
必须先把转义解回再断言。

### 守卫实现上的两个坑（都已被测试钉住）

1. **判据不能用 `\w`** —— Python 的 `\w` 含 CJK，"幂运算符判据"会把 `页**刻**分` 判成
   合法的 `2 ** 3`，**中文强调全部漏报**。一律用 ASCII 字符类。
2. **扫描器必须先穿正则字面量** —— `esc()` 里的 `.replace(/"/g, '&quot;')` 会让扫描器
   在 `"` 处开字符串、一路吞到 `'<div class="'`，这段里夹的
   `// ...**不能用 toISOString()**...` 注释就被当成界面文案报出来。
   另有：docstring 里写 `` `\w` `` 会触发 `SyntaxWarning: invalid escape sequence`
   （用 `-W error::SyntaxWarning` 才抓到），改原始字符串解决。

## 深夜续二：`fenjin120 不可用` 根因查明（腾仔）

阿勇问「fenjin120 不可用 是什么原因」。**不是故障，是刻意的降级 + 一个从未被创建的数据文件。**
